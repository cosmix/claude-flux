Lanes, with model and effort read as one row

The two ideas do not compete: lanes are the columns, pairs are the rows. Each lane splits into a model and an effort sub-column for the pressure and models sections, so a stage type reads as one line across all three files. The winner is marked under each control, not each row, because knowledge_model and knowledge_effort resolve independently: a stage can take its model from your user file and its effort from the built-in. The key cell states the resolved pair, so the answer is readable even when it is split across lanes.

This mock is live: change a select, edit a number, flip a switch, or clear a value with ✕. Writes take half a second and can fail, as they can against the real API (try a non-number in a numeric field). The full registry of eighteen keys is here.

How to read a row
  • Left to right is resolution order. The underline sits under the control that is speaking.
  • Lanes alternate ground, carry a hairline at every boundary, and wear their tone as a bar over the head. A solid control border means this file names the value; dashed means it shows what falls through.
  • The project lane for a user-only section is one aurora-ui empty state spanning the section, instead of a dash on sixteen rows.
  • The filter box takes / from anywhere in the dialog and matches names, help, and values at any tier, so "sonnet" finds every key that resolves to it.
What the registry must know
  • Pairing is by suffix: a section whose keys all end in _model or _effort renders as pairs, with the shared prefix as the row label. Nothing changes on the wire.
  • Row labels are the prefixes: standard, knowledge_distill, and for pressure claude, codex, address. The help text for the row is the model key's help with "model" stripped, or a short caption table in the frontend.
  • A section with a stray unpaired key falls back to single rows, so a new key never breaks the layout.
Behaviour kept from today
  • One key per write, keyed by scope and name, pending value shown until the server answers.
  • A rejected write keeps the draft and shows the validator's message; Escape drops the draft, a second Escape closes.
  • Clearing previews the fallback value, then the server's answer replaces it.

Below about 700px the table turns on its side

Seven columns cannot fit in 390px, and a horizontal scroll would hide the project lane exactly where it matters. Instead each row becomes a card and the cascade runs top to bottom: built-in, user, project. Model and effort stay side by side inside the card, so a stage type is still read as one pair. The underline and the resolved pair in the card header carry over unchanged. This phone is live too, and shares state with the table above.

What changes
  • The lane headers become a legend under the title, and each tier's label carries the lane's tone square.
  • The hatched "user only" region becomes a note on the section line, and the project tier is simply absent from those cards.
  • Cards are 42px per tier: a paired card is about 150px, a singleton about 110px. The registry runs about 2,000px, which is a normal phone scroll.
What does not
  • Same controls, same states, same per-control underline, same writes.
  • The breakpoint is a CSS media query over one component; both layouts render from the same entries and statuses.
  • Number fields keep inputmode="numeric" so the phone opens a digit keypad.
Between the two
  • From 700px to about 960px the table drops the built-in sub-columns to a single read-only pair ("opus · high") to save 60px, then the cards take over.
